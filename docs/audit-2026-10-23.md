# Repository-Audit vom 23. Oktober 2026

Fünf Sub-Agents prüften Katalog, Einkauf/Sync, Web/PWA, CLI/Client und
Installation/Updates. Der Hauptagent prüfte API und Integration. Die Prüfung
umfasste Laufzeitcode, Templates, statische Assets, Installer, Packaging,
CI-Skripte, Tests und aktuelle Betriebsanleitungen. Gegenreviews prüften die
Änderungen an Katalog, Transaktionen, API und Client nochmals unabhängig.

Alle Reproduktionen und Browserläufe verwendeten eigene Daten unter `.tmp/`.
Die installierte Haushaltsinstanz und die Beispieldaten im Repository wurden
nicht verändert.

## Behobene Fehler

| Bereich | Fehler und Korrektur |
| --- | --- |
| Einkaufs-PWA | Voller oder gesperrter Browser-Speicher ließ Änderungen beim nächsten Rendern verschwinden. Die offene Seite hält den letzten Stand jetzt im RAM, synchronisiert weiter und kehrt nach erfolgreichem Schreiben zur Speicherung zurück. Ein ungesicherter RAM-Stand überlebt kein Neuladen. |
| Sync-Identität | Die gültige ID `__proto__` verschwand aus einer JavaScript-Objektmap. Die ID-Map hat jetzt keinen Prototyp. |
| Zeitstempel | Extremwerte konnten beim UTC-Konvertieren oder Fortschreiben mit einem Overflow abstürzen. Nicht fortschreibbare gewinnende Remote-Versionen werden vor dem Speichern abgewiesen; beschädigte Altwerte bleiben durch normale Änderungen reparierbar. |
| Favoriten | Mehrzeilige Aliasse wurden beim Anlegen akzeptiert, beim späteren Hinzufügen abgelehnt. Beide Wege validieren jetzt gleich. |
| Mutationsfehler | Fehlgeschlagene Bildbereinigung nach gespeichertem Zustand verlor das Änderungsereignis und meldete die Teilwirkung nicht. Solche Fehler veröffentlichen weiterhin eine Änderung und werden als `outcome_unknown` gemeldet. Vollständig zurückgerollte Vorgänge erzeugen dagegen weder Teilwirkungsmeldung noch Ereignis. |
| Bildimport | Abgebrochenes Kopieren konnte unreferenzierte Teilbilder hinterlassen. Importpfade räumen fehlgeschlagene Kopien auf, melden gescheiterte Bereinigung als Teilwirkung und behalten Bilder, deren Metadaten bereits gespeichert wurden. |
| Diagnose | Ungültiges UTF-8 in Rezepten und Dateien an Verzeichnispfaden brachen `check` ab. Sie erscheinen jetzt im Diagnosebericht; die übrige Prüfung läuft weiter. |
| Historie | Sehr große positive `--days`-Werte verursachten einen Kalenderüberlauf. Solche Fenster umfassen jetzt die gesamte verfügbare Historie. |
| API | Synchrone Dateioperationen und Sperrwartezeiten in asynchronen Routen blockierten den Server-Eventloop. Befehle, Sync-Arbeit und SSE-Dateilesungen laufen jetzt in Worker-Threads. |
| Request-Grenze | Das Größenlimit vertraute allein auf Content-Length. Es wird jetzt zusätzlich beim Einlesen der tatsächlichen Bytes durchgesetzt. |
| Web-Rücksprung | Backslashes oder Steuerzeichen konnten einen scheinbar lokalen Rücksprung in eine externe URL verwandeln. Diese Ziele werden verworfen. |
| Editor | `EDITOR` mit Argumenten, etwa `code --wait`, wurde als einzelner Dateipfad gestartet. Native Windows- beziehungsweise POSIX-Argumentbehandlung unterstützt jetzt Kommandos und Pfade mit Leerzeichen. Fehler erhalten weiterhin die Recovery-Datei. |
| Installation | Der Checkout oder PYTHONPATH konnte eine leere Runtime als verwendbar erscheinen lassen. Installations-/Reparaturprüfungen importieren isoliert mit `-I`; der Packaging-Test prüft tatsächlich das gebaute Wheel. |
| IPv6 | Ein Dienst auf `::` wurde über IPv4 geprüft. Die lokale Adresse verwendet jetzt `[::1]`. |
| Konkurrenztest | Der Update-Sperrtest setzte voraus, dass alle Prozesse innerhalb von 200 ms starten. Eine explizite Freigabe nach allen Sperrversuchen ersetzt diese Zeitannahme. |

## Performance

Lokale Windows-Messungen auf identischen Wegwerfdaten. Die Zahlen sind
Szenarienmessungen, keine allgemeine Beschleunigungszusage.

| Szenario | Vorher → nachher | Aussage |
| --- | --- | --- |
| Suche in 1.500 Rezepten, Treffer bereits im Titel | 704,8 → 6,8 ms | Median aus drei alternierenden Läufen mit alter/neuer Funktion. Markdown wird nur gelesen, wenn Titel und Tags die Suchbedingung noch nicht entscheiden. Zutaten-Suchen benötigen weiterhin die Rezepttexte. |
| Unveränderter Sync mit 10.000 Items einschließlich Tombstones | 136,9 → 97,3 ms | Median aus neun Läufen; die alte zusätzliche Speicherstufe wurde nachgestellt. Kein erneutes Serialisieren und Dateilesen bei unverändertem Stand. |
| Client-Transport eines 32-MiB-JSON-Payloads, simuliertes Netzwerk | 168,2 → 81,9 ms | Median aus fünf Läufen. JSON wird einmal statt zweimal kodiert; kein gemessener Rückgang des Speicherpeaks. |
| Duplikatscan in 1.500 Katalogeinträgen | 98,4 → 0,113 ms | Linearer Zähler ersetzt quadratische Suche. Die gesamte Integritätsprüfung bleibt durch Datei-I/O bestimmt; dafür ist kein Gesamtgewinn belegt. |

API-Aufrufe ohne Anhänge erzeugen keine temporären Anhangsordner mehr.
Der Client liest Bilddateien höchstens bis 25 MiB plus einem Prüfbyte und
weist Übergrößen vor Base64-Kodierung und Versand ab.

## Verifikation und Grenzen

Die Regressionen prüfen unter anderem fehlgeschlagene Storage-Schreibvorgänge,
Offline-Änderungen und spätere Synchronisation, opake IDs, Teilwirkungen und
Rollback, beschädigte Rezeptdaten, erhaltene Editor-Recovery-Dateien,
Request-Streamlimits und die Reaktionsfähigkeit des Eventloops. Der
Service-Worker-Cache wurde auf v17 erhöht. Agent-Guides, Skill und Domain Maps
wurden mit den betroffenen Verträgen abgeglichen.

endete mit Status 0: alle 18 Testscripte mit zusammen 1.962 Checks, 133
Browserchecks und 72 PWA-Checks bestanden. Zusätzlich wurden Live-Suche und
mobile Einkaufsliste über den lokalen `playwright-cli`-Skill in Edge angesehen.
`git diff --check` meldete keine Whitespacefehler.
