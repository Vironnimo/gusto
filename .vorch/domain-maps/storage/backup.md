# Household backup and restore

`gusto/core/backup.py` creates a portable ZIP, previews its restoration and replaces the household store after a matching preview. The archive includes the five domain JSON files, active Markdown, images and archived recipes; it excludes lock files, the change journal, runtime settings, shopping generation and previous safety backups. Empty directories are not represented. A snapshot acquires all four resource locks to capture consistent bytes.

The version-1 manifest lists every payload path, byte length and SHA-256. Restore rejects unknown or nonportable paths, case-insensitive duplicates, links, encrypted files, mismatched manifest records, corrupt ZIPs, and data exceeding the limits of 64 MiB compressed, 32 MiB per file, 128 MiB total, 2 MiB manifest and 25,000 files. The in-memory implementation holds multiple copies within those limits; this is a bounded small-household design, not a streaming archive. A separate Python process checks a staged store with its own `GUSTO_HOME`, validates metadata paths, and uses the existing `checks.check()` integrity rules. Errors reject both ordinary backup creation and restore; warnings are included in the preview. No process-global environment change is used in the service.

`preview_restore(bytes)` returns `token`, counts, warnings and added/replaced/removed file counts. The token binds exact archive bytes, all current household file contents and the current shopping generation. `restore_backup(bytes, token)` repeats validation, takes all resource locks and rejects a stale token. It writes and verifies a safety ZIP in `backups/<id>.zip` before replacing domain files and trees. The safety ZIP captures the existing bytes even if the current store is inconsistent; its manifest verifies their preservation, but later restore still enforces integrity checks. Restore retains the original `data/` directory, lock files and change journal, resets the shopping generation under the same transaction, and emits one change event for all four resources. `read_safety_backup(id)` checks and serves a generated safety copy. Safety copies are outside the household payload, so they do not recursively grow subsequent backups.

Replacement failures restore the previous files and generation in reverse order. A complete rollback emits no change event and leaves the safety ZIP available on disk. If rollback itself fails, the transaction directory remains under the data root; the error names its path and storage reports an uncertain outcome. Abrupt process termination can interrupt multi-file replacement and requires manual recovery from the retained safety ZIP or transaction directory; this protocol is not a crash-atomic filesystem transaction. Concurrent lock-free readers can observe intermediate states during replacement, as with other multi-file operations.

`tests/test_backup.py` exercises public backup/preview/restore behavior against throwaway stores, including stale previews, validation and injected rollback failures.
